# 背景与产品愿景

记录日期：2026-11-07。本文整理用户在前期讨论中提供的背景，并保留产品形成的原因。公司名称未提供。

## 团队与发起人

团队位于某公司服务器部门的 CSP（Cloud Service Provider）Team 下，属于 Product Assurance 的 Automation Team。

Automation Team 开发自动化脚本、自动化测试系统和 Web 平台，帮助测试工程师完成测试。脚本同事可能涉及 BIOS、BMC、Performance 等方向。

产品发起人主要从事后端及软件平台开发，开发前后端分离系统，管理项目、Case，并支持从页面执行自动化 Case。发起人不以编写硬件测试脚本为主要工作。

公司已配备 GitHub Copilot 和 Microsoft Copilot，发起人日常高频使用 GitHub Copilot。后续已确认使用 VS Code、Copilot Pro，并选择 Python 自建示例作为试点；用户确认公司环境允许本地 Agent Plugin、本地工具和 MCP。本机版本及真实验证结果见[环境验证记录](11-environment-readiness.md)，该结果不外推到其他电脑。

## 触发事件

部门近期频繁组织 AI 技术分享，主题是让 AI 进入日常工作、提升效率。

一次分享中，FW engineer 展示了利用 GitHub Copilot 开发脚本，以及一个 SAS Expander AI 助手。根据用户转述，该助手能够生成脚本、触发测试、生成报告并上传 Jira。分享者声称，某项任务由原本约 2 天缩短到 16 分钟。

管理者对结果满意，随后质疑 Automation Team 的部分脚本开发工作是否仍然需要人工承担。

用户关注该案例是否涵盖需求澄清、代码 Review、异常场景、后续维护等工作，以及单一简单场景的收益是否能够外推到整个部门。这些是需要核验的问题；当前没有同口径的原始数据，不能据此确认对方夸大，也不能据此证明全部脚本工作已被替代。

这段经历作为内部立项背景保留。面对团队或管理层介绍时，重点呈现可验证的产品收益和合作机会，不把未经证实的个人动机推断写成事实。

## 初期思路与演进

初期考虑过分享 Skill 开发、MCP Server、AI 代码质量、Review、项目知识管理和长期记忆。

发起人已有公开项目 [engineer-voice](https://github.com/yanlong-l/engineer-voice)，用于改写已有技术文本：把抽象表达展开为具体对象、动作和条件，保留事实、代码、数值和不确定性。

讨论进一步形成一个整体产品方向：工程师只安装一个工具包，通过一个入口获得开发、Review、文档及续接支持。产品可以使用 Skills，但希望提供比单独 Skill 更完整的 Agent 体验，减少用户选择和组合大量 Skills 的负担。

用户还提出自动生成页面，帮助工程师理解 AI 参与生成的代码，以及支持个人工作流和可插拔选项。

名称已经确认：仓库 `engineering-flow`，产品 **Engineering Flow**。`engineer-voice` 保留原名，作为拟集成模块。

## 产品愿景

让工程师读懂 AI 的改动，让 AI 接得上工程师的工作。

工程师与 Copilot 开始一个任务时，能够取得相关背景、已有设计和明确的验收条件。开发以后，能够查看真实改动及验证结果。隔了一段时间、换了会话或换了维护者，仍能找到适用的设计决定、限制和下一步工作。

产品关注完整交付过程的效率，包括理解、验证、返工和维护成本。

## 目标用户

| 用户 | 需要的支持 |
| --- | --- |
| 使用 Copilot 的开发工程师 | 少重复解释、少遗漏要求、更方便理解和验证改动 |
| Review 人员 | 快速定位关键代码，核对需求、检查结果和未验证事项 |
| 长期维护者 | 了解已有设计及其依据，识别过期信息，继续工作 |
| Automation / PA 团队 | 将工程经验用于更多项目，并验证收益 |
| 团队负责人 | 看到可重复使用的成果及完整交付指标 |

首批验证场景来自测试平台的软件开发。产品后续可以服务其他软件项目；跨语言、硬件测试和团队级服务暂不作为首版承诺。

## 成功的表现

- 同事能更快找到关键改动，并能指出实际缺陷或未验证事项。
- 检查结果与当前代码对应；代码改变后不会沿用旧的通过状态。
- 新会话能够恢复有效上下文，且不会把旧分支或待确认记录当成现状。
- 文档反映真实行为，同时没有给日常小改动增加大量维护工作。
- 多位工程师能够重复采用默认流程，并按项目需要进行有限定制。

## 对组织的价值

Automation Team 可以把已有编程和平台经验用于统一工具、执行记录、评审支持和助手验收。FW、BIOS、BMC、Performance 等同事可以贡献领域规则与案例，共同验证助手的有效范围。

部分脚本编写工时可能被 AI 压缩，团队的实际贡献需要通过新成果证明。工程能力的价值体现在交付可靠工具、支持更多工程师使用，以及降低整个交付过程的理解和返工成本。
