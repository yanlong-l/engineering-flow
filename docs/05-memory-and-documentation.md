# 项目记忆与文档管理

状态：M3 已实现本地候选记忆、来源读取、显式关系、上下文选择、文档建议与交接；engineer-voice 以固定 Markdown Skill 显式加载，宿主 Agent 负责实际改写。实际验收见 STATUS，团队共享与正式插件仍待后续实现。

## 目标

让下一次工作获得足够且适用的信息，同时控制过期内容、上下文体积和维护成本。保存全部对话不是默认方案。

## 记录分类

| 类型 | 示例 | 默认处理 |
| --- | --- | --- |
| 任务进度 | 完成了接口，尚缺重复请求检查 | 自动保存，完成后归档 |
| 程序观察 | 某命令的实际运行结果、接口实现位置 | 自动保存来源和快照 |
| 解释性判断 | 该设计可能用于防止重复提交 | AI 提议，不能自动成为事实 |
| 设计决定 | 为什么选择请求标识，接受什么限制 | 草稿随代码 Review 确认 |
| 项目约定 | 允许的状态转换、检查方法 | 版本化维护，记录来源 |
| 个人偏好 | 中文说明、较简短页面 | 个人配置，不混入团队决定 |

## 记录的可信状态与适用状态

两个维度分别记录：

- 确认状态：`proposed`、`confirmed`、`rejected`。
- 适用状态：`current`、`needs_revalidation`、`superseded`、`archived`。

“已确认”不等于永远适用；“需要复核”也不等于原记录已被证明错误。替代旧记录时保留关联和原因，避免两个互相冲突的决定同时作为默认上下文。

记录至少包含内容、类型、模块或路径范围、来源引用、确认信息、最后核验时间及对应快照。来源可以是代码、实际执行结果、PR 或明确的人类决定。仅有模型置信度不构成来源。

## 自动保存与确认

程序自动保存任务进度、工具结果、代码引用和候选记忆。对具体设计理由的归纳先作为候选。

人工可以在现有 Review 流程中确认设计决定与文档修改，不需要每条记录弹出额外确认框。未经过该过程的候选保持待确认状态；模型不能通过自评提升为人工确认。

## 检索流程

1. 核对当前项目、worktree、任务和代码状态。
2. 根据需求、关联路径和模块筛选记录。
3. 优先选择适用的已确认决定和可追溯事实。
4. 对候选、冲突和过期记录附状态说明；必要时先读当前代码复核。
5. 按配置的输入预算返回简短内容、来源和可继续读取的引用。

不把全部历史合并成一个不断增长的 Markdown。被预算排除的相关项应可继续检索；不能声称已经考虑了未加载的全部信息。

## 过期、冲突与清理

相关代码或配置变化、引用删除、设计决定被替代时，标记需要核验。按时间清理适用于临时进度和缓存，不能仅凭时间自动宣布设计事实仍然有效或已经错误。

两条记录矛盾时列出来源与版本，优先核对当前实现和已确认决定。如果实现与决定不一致，指出差异，不擅自把其中一方改写为正确。

相似记录可以建议合并，但不能丢失适用条件、否定、时间范围和来源。归档记录不参与默认检索，仍可追溯。

## 存储与团队共享

建议区分以下位置，名称在实现时确定：

- 本地运行目录，例如 `.engineering-flow/`：任务进度、执行输出、页面和可重建缓存，默认不提交。
- 仓库中的工程文档，例如 `docs/engineering-flow/`：经过 Review 的设计决定和维护知识，随代码提交。
- 项目配置：共享命令及流程要求。
- 个人配置：用户偏好和本机路径，不写入团队记录。

安装目录只存产品代码，不保存项目状态。共享文档与本地索引通过稳定 ID 和来源关联；避免人为维护两份同义正文。

本地 `.engineering-flow/` 和根忽略规则已经实现；仓库内共享记忆文档、同步索引与个人配置仍属规划。

## M3-1 已实现的操作与边界

- `memory propose` 显式保存候选；正文为调用者输入，origin=caller，不假定作者为人或 AI，不接受自报确认状态/身份。类型支持 explanation、design_decision、convention、limitation，其他分类继续使用已有任务和检查记录。
- 来源支持同任务、同快照的实际代码行、终态检查或评审事件，保留各来源 origin 和快照。运行中的检查会变化，不接收为不可变来源。失败检查、跳过、AI 解释和调用者意见都保留实际含义，不能证明候选正文正确；PR 认证或外部决定来源尚未实现。
- `review record --memory` 的意见绑定原始记忆内容、快照及任务修订，通过已有 `review confirm` 记录独立本地终端回执；确认状态与适用性分别计算。确认时间和 OS 来源来自回执，assurance=local_session_not_identity_verified。任务批准不自动确认记忆；一组候选中后续单条确认只替代对应条目。仍不构成身份认证。
- `task start/checkpoint/resume` 返回 `memoryContext`；`memory context` 可传路径、模块、查询词和字节预算。任务关联、父子路径匹配、显式模块标签、casefold 关键词和 project 范围决定相关性，不做向量或语义检索。先排序适用且无冲突的已确认记录，再按任务、路径、模块、关键词分值与稳定 ID 排序。
- 只限制 selected 的规范 UTF-8 JSON 字节数，不把字节数当模型 token 数。候选、过期和冲突项带状态提示，只有 eligibleAsCurrentBackground=true 才是当前已确认背景；预算遗漏及其他排除项有原因和继续读取命令。元数据、排除列表、关系和任务正文不在预算内；complete 只表示相关记录是否因预算遗漏。
- 完整声明快照或所属任务修订改变后保守 needs_revalidation；不把旧内容重写为新结论。删除来源仍可读原快照。复核需重新读取当前来源并提出新候选，再建立替代关系；没有自动复核或原位编辑正文入口。
- `memory relate` 保存 conflicts_with、supersedes、archive 及原因。关系是调用者声明，不冒充程序识别出语义矛盾。未确认替代候选保留旧项并提示差异；新项曾获明确批准后旧项退出默认上下文，后续撤回/归档新项不自动恢复旧规则。冲突双方仍可追溯，不隐式合并；禁止循环、自关联及跨分支/工作区关系。
- 数据仅保存本地 SQLite，缺少 Hooks 时仍可显式完成；不采集全部对话、不上传、不新增模型服务。没有自动候选提取、共享文档、全文索引分页、归档撤销或垃圾回收，大历史性能未专项验收。

可运行格式与命令见 [README](../README.md)，构造来源样例见 `examples/batch-queue/memory.example.json`。

## 文档更新策略

默认更新现有说明。下列变化通常需要检查文档：

| 变化 | 检查的文档 |
| --- | --- |
| API 行为、参数或错误处理 | 接口说明与调用示例 |
| 数据结构或迁移 | 数据说明、部署与兼容性说明 |
| 运行和检查方法 | 开发、部署、排查手册 |
| 重要设计取舍 | 对应设计决定 |
| 普通局部修复 | 必要的任务及 Review 记录 |

文档分为人工维护、完整生成和混合三类。人工维护部分提供可审阅修改；完整生成部分标记来源；混合文档只更新约定区域。生成页面读取同一份结构化材料，不再单独维护一份解释。

M3-2 使用 `document propose/show/export` 保存不可变建议，只处理调用者明确给出的目标和原因，不自动推断全部受影响文档。target/mode/region/draft/reason/sources/protectedFacts 为固定输入；来源与任务/快照规则复用记忆。人工文档保留完整修改前后内容；生成文档必须新建或带有明确的生成标记；混合文档只替换唯一的命名区域，其余字节保持原样。全部模式均只导出原文、建议和 patch，不覆盖工作区。完整格式及标记见 README。

`review record --document` 把原文、草稿、候选、来源与摘要纳入原有意见范围，再由同一个本地终端入口确认，不新增身份或确认系统。确认状态与适用性分开：完整声明输入、任务修订或相关检查来源变化后 needs_revalidation，旧内容和确认不改写。任务或文件批准不自动确认建议，建议批准也不意味着已应用或检查通过；应用后需要对新快照重新检查和评审。分组确认按每条建议独立计算。

`task handoff` 共用 Review 生成，输出 handoff.md/json、完整 Review 与文档建议包。交接包含目标、调用者进度/下一步、未决事项、运行证据、确认范围、文档状态和预算内的记忆上下文；原始 JSON 中可继续读取预算排除项。生成材料绑定一次快照和任务修订，完成状态不被断言。没有自动应用、语义比对、团队同步、分页或垃圾回收。

## engineer-voice 集成

项目来源：[yanlong-l/engineer-voice](https://github.com/yanlong-l/engineer-voice)。M3-2 已核对并收录 v0.2.0、提交 `8dcf520fb3974e9711cf193ca78a9839a7fce5f0` 的原创规则、词表、构造样例、七组回归材料与 MIT 许可；具体范围见根目录 THIRD_PARTY_NOTICES。文件哈希和固定清单在加载前核对。它不是可执行重写程序，不提供独立模型服务。

已实现流程：完成技术草稿与来源核对 → `document voice` 显式加载已校验 Skill → 由当前宿主 Agent 按规则改写 → `document rewrite` 提交绑定原建议和模块摘要的候选 → 程序检查保护内容 → 纳入 Review 核对技术语义。loaded 仅表示模块读取成功，modelExecution 始终为 not_observed，不能当作实际模型执行凭证。

适用内容包括 PR 描述、Review 说明、设计决定和维护文档。代码、命令、原始日志、结构化状态和实际检查结果保持原样。模块不替代代码检查和事实核验。

集成时选择固定提交或版本，保留适用的许可与来源。模块更新需要运行语义回归样例，特别检查“未确认”与“未发生”、“超过”与“达到”、部分暂停与全部停止等差异。版本升级不能默默重写已经确认的历史决定。

程序保守比较常见 Markdown 保护区、数值及已识别单位、敏感词序和显式逐字事实。变化时保存 rejected 候选、原因和原技术草稿，after 采用原稿；模块缺失/损坏时 unavailable，直接返回原稿，不补造改写。保护检查通过仍是 proposed，不推导语义等价；主体、对象、因果、未知 Markdown 或单位仍需 Review，含义相同的词语变化也可能被保守拒绝。七组固定文本检查与宿主模型行为验收分开记录，不能以程序回归替代真实 Copilot 验收。

## 与 Copilot 原生记忆的关系

可以利用原生 Memory 作为辅助，但不把其可用性、写入和每次检索作为产品必须满足的条件。Engineering Flow 的重要项目记录应当可查看、可审阅，并能在显式续接时读取。

原生记忆的覆盖客户端、设置和管理方式需要按实际环境核验。[GitHub 官方说明](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory)
