# Review 页面与工程师体验

## 页面目的

帮助工程师找到需要判断的位置，理解本次改动与需求的关系，核对实际检查结果。页面降低寻找信息的成本，评审结论仍由工程师根据代码和结果作出。

首版按任务生成本地 HTML，固定模板渲染结构化材料。下面是页面设计，不是已完成页面。

## 建议信息布局

```text
Engineering Flow · 当前任务
需求摘要 | 代码快照 | 页面生成时间 | 是否需要刷新

概览 / 改动与阅读路线 / 验证结果 / 待判断事项 / 文档与交接

需求与行为
  要求实现什么、实际做了什么、尚缺什么

建议阅读路线
  入口 → 业务处理 → 数据或任务状态 → 异常返回
  每项附文件、正确快照中的代码及 diff

需要人工判断
  具体问题、影响、相关实现、已有检查、未覆盖场景

验证结果
  已通过 / 失败 / 执行错误 / 未运行 / 跳过 / 已过期
  命令、代码快照、输出引用

设计与维护
  已确认决定、候选修改、文档差异、下一步
```

## 按行为解释改动

同一行为可以横跨多个文件。页面应说明工程师按什么顺序阅读，以及每处修改与需求的关系，不只逐文件重复代码。

首版只承诺有引用的文件和 diff 路线。跨语言的完整调用图、运行时路径和系统影响分析属于增强能力；模型推测的关系需要标明，不能画成已经证实的执行链。

## 贯穿示例

构造需求：批量执行 Case；页面超时重试时，同一个操作不能重复创建任务。

一个 Review 项可以呈现：

| 字段 | 示例内容 |
| --- | --- |
| 需要判断 | 两个服务实例同时收到相同请求时，是否创建两批任务？ |
| 关联位置 | 任务创建接口、请求标识校验、持久化操作 |
| 已有检查 | 同一实例中连续提交同一个请求标识 |
| 尚未覆盖 | 多实例并发提交 |
| 工程师操作 | 查看 diff、查看运行输出、记录问题或显式确认 |

此例仅用于说明布局。没有实际执行前不能显示上述检查已经通过，也不能无依据地宣称发现了缺陷。

## 来源展示

页面把以下内容分开呈现：

- AI 解释：对代码、流程或风险的理解，附相关引用及未确认点。
- 程序观察：检查命令、原始结果、快照、文件变化。
- 人工确认：谁通过什么显式操作确认了哪一范围和快照。

不用一个总分替代这些信息。自动化检查通过不隐藏未覆盖场景；没有问题报告也不等于代码已获批准。

## 过期与错误

- 页面显示对应代码快照和生成时间。
- 当前代码改变时，将旧说明、检查或评审标为需要重新核验。
- 引用不存在或行号无法映射时，显示引用失效，不跳到看似接近的位置。
- 跳过检查显示原因；检查执行错误与业务断言失败分别显示。
- 页面材料生成失败时，仍能读取任务和原始检查结果。

纯静态页面不能实时观察仓库。首版可通过显式刷新重新检查状态；未刷新时保留“生成时快照”，不展示无依据的“当前全部有效”。

## 交互设计

首版提供筛选、展开 diff、读取输出和复制交接说明。人工评审写入由显式 CLI 或已存在的 PR Review 操作完成。

若希望在页面中直接保存意见，应实现实际的本地写入通道及调用来源校验，或使用 VS Code Webview 消息通信；不能在静态 HTML 上放一个没有持久化行为的“确认”按钮。

后续可增加 IDE 中的代码跳转、针对关键行为的问题提示和变更后的实时刷新。点击阅读或回答几道问题不自动证明理解，也不作为工程师绩效指标。

## 渲染要求

代码、日志、文档和模型文字均按内容转义，不作为脚本执行。页面默认不请求外部资源。首版按本地使用设计；若增加服务，限制绑定和可访问路径，写操作由明确的产品接口处理。

## 页面验收

1. 对同一结构化输入，能得到完整且稳定的布局。
2. 需求、实现和检查能互相定位。
3. 失败、错误、跳过、未运行和过期不被合并为通过。
4. 快照切换以后，代码引用和评审状态对应正确版本。
5. 原始输出包含 HTML 或脚本样式文本时仅作为文本展示。
6. 静态页面与实时界面的能力说明符合实际实现。
