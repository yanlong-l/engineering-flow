# 产品需求与首版范围

本文中的 P0 是建议首版验收要求，P1 是后续增强，P2 是较长期选项。具体实现顺序见路线图。

## 用户主路径

1. 安装产品并检查当前 Copilot 环境的可用能力。
2. 关联当前仓库，配置必要的开发与检查命令。
3. 开始或继续任务，明确本次行为和验收条件。
4. 加载相关项目知识，配合 Copilot 实现和验证。
5. 生成 Review 页面，工程师核对代码并提出意见。
6. 修订后刷新验证结果与页面。
7. 完成必要文档修改和交接；以后可从新会话恢复。

用户不需要在每个阶段挑选 Skill。未明确的需求只有在影响实现时才澄清，普通项目约定可以从现有代码和文档中取得。

## 开发质量支持

开始实现前取得明确的期望行为和可验证条件，阅读相关现有代码及检查方式。新增功能尽量分成范围清楚的改动，避免混入无关重构。

按具体功能考虑失败路径，例如权限不足、超时重试、重复提交、任务状态变化。检查范围与实际风险相适应，小改动不强制产出长方案。

AI 生成的说明应回答：改了什么、为什么、如何检查、仍有哪些限制。由 AI 生成的测试仍需核对断言是否来自需求，不能因为代码和测试同时通过就认定需求一定满足。

## 首版体验约束

- 产品能力完整，但只承诺一种经过验证的客户端环境和一个试点技术栈。
- 不为日常使用增加独立账号体系。
- 本地 Core 处理状态与记录；推理优先沿用已有 Copilot。
- 日常保存和更新尽量自动执行；语义决定通过现有 Review 过程确认。
- 没有检查结果时显示未运行，不能用 AI 解释填补。
- 页面不把点击“已阅读”解释为已经理解或代码没有问题。
- 软件停止运行后不承诺继续执行；后台服务属于后续明确设计。

## 首版不包含的能力

- 重建 Copilot 或训练自己的基础模型。
- 安装后自动接管所有 Copilot 会话、IDE 和云端 Agent。
- 自主生成并在真实设备上执行任意测试脚本。
- 自动批准合并、自动发布或未经配置的外部写操作。
- 多租户 SaaS、公司级知识库、全语言语义分析。
- 以向量数据库或多 Agent 并行为必要前提。
- 自动证明所有代码正确，或保证所有长期记忆永不过期。

## 默认工作量控制

| 任务规模 | 默认产出 |
| --- | --- |
| 小修复 | 简短任务记录、相关检查、简洁 Review 页面 |
| 一般功能 | 行为说明、相关设计信息、检查与未覆盖场景 |
| 跨模块或状态复杂的改动 | 额外设计决定、影响分析和专项检查 |

系统可以建议任务规模，但不能只靠文件数量判断复杂程度。工程师可以调整；必需检查仍按项目规则执行。

## 验收边界

“可用”指在明确环境中重复跑通，而不是文档中定义了某个能力。“自动”需要说明由什么事件触发、是否依赖产品正在运行，以及失败或缺少支持时如何继续。
